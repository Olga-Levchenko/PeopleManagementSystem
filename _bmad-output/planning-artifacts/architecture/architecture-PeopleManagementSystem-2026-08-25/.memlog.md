# Architecture Spine Memlog

- 2026-08-25 | direction | Scope: initiative-level architecture spine for the People Management Platform; purpose: build substrate; audience: the four-person implementation team and downstream BMAD story builders.
- 2026-08-25 | constraint | The finalized PRD, project requirements, and section access matrix are governing inputs; Sections 2 and 3 of the requirements are normative.
- 2026-08-25 | constraint | The approved architecture is service-oriented bounded contexts in one shared monorepo and local development platform, with thin pragmatic boundaries and independent deployability where useful.
- 2026-08-25 | decision | Use React for the frontend; use Keycloak for authentication; keep Authorization as a separate .NET bounded context; use Node.js/TypeScript for core business/domain APIs; leave integration-worker technology open.
- 2026-08-25 | decision | Use People/Organization, Authorization, Work Management, Resourcing, and External Integrations as the initial bounded contexts.
- 2026-08-25 | decision | People/Organization owns employee profiles, employment history, organization structure, reporting lines, departments, projects, assignments, People Partner relationships, and authoritative organizational relationships.
- 2026-08-25 | decision | Authorization owns resolved access roles, functional permissions, section/record/operation policy decisions, and an authorization-focused derived relationship projection; it does not own source relationships.
- 2026-08-25 | decision | Use RabbitMQ for normal asynchronous propagation, versioned message contracts, idempotent consumers, retries, dead-letter handling, and replay-safe processing.
- 2026-08-25 | decision | Authoritative event producers use transactional outboxes so committed relationship changes and corresponding domain events cannot diverge.
- 2026-08-25 | decision | Access-revoking relationship changes receive priority propagation and fail-closed treatment while authorization freshness is uncertain; synchronous People lookup is exceptional, not the default.
- 2026-08-25 | decision | Use a BFF/API gateway as the browser-facing boundary: validate Keycloak tokens, call and compose domain APIs, return consistent errors, and never own or bypass authorization policy.
- 2026-08-25 | decision | Use PostgreSQL with service-owned databases or schemas; a shared physical instance is allowed initially, but services must not access another service's tables.
- 2026-08-25 | decision | Use versioned REST/JSON APIs with OpenAPI contracts and consistent error envelopes.
- 2026-08-25 | decision | Use Docker Compose locally, per-service migrations, health/readiness checks, structured correlation-aware logs, practical tracing, and CI gates for builds, unit, integration, contract, migration, and focused end-to-end tests.
- 2026-08-25 | constraint | Authorization testing must assert API response behavior for relevant audience, relationship-path, and section combinations, including negative-access cases; the access matrix remains the source of truth.
- 2026-08-25 | question | Establish the exact bounded revocation propagation target, freshness telemetry, and operational alert thresholds before production deployment.
- 2026-08-25 | question | Select concrete framework versions, integration-worker runtime, deployment provider, and complete RabbitMQ topology during implementation foundation work.
- 2026-08-25 | event | ADR-001 accepted: Authorization Projection Consistency and Revocation Propagation.
- 2026-08-25 | event | Architecture spine finalized.
